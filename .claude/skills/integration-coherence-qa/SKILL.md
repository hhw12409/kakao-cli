# 통합 정합성 QA

kakao-cli에서 런타임 버그의 1순위 원인은 **경계면 불일치** — 공통부와 어댑터가 각각 "맞게" 구현됐지만 연결 지점에서 계약이 어긋나는 것. 2순위는 **플랫폼 갈라짐** — macOS와 Windows가 같은 명령에 다르게 반응하는 것.

검증의 핵심 질문은 "이게 존재하는가?"가 아니라 **"생산자의 출력이 소비자의 기대와 정확히 일치하는가?"**

## 왜 정적 리뷰·빌드 통과로는 못 잡나

- 타입 캐스팅/제네릭/`any`가 쓰이면 shape이 어긋나도 컴파일러가 통과시킨다.
- 각 컴포넌트를 개별로 보면 다 정상. 어긋남은 **연결 지점**에만 있다.
- "어댑터 함수가 있는가"와 "그 반환값이 공통부의 파싱 기대와 맞는가"는 전혀 다른 검증.

## 검증 방법: 양쪽 동시 읽기

경계면은 반드시 **양쪽 코드를 같이 열어** 비교한다. 한쪽만 읽으면 못 잡는다.

| 검증 대상 | 왼쪽 (생산자) | 오른쪽 (소비자) |
|----------|-------------|---------------|
| 어댑터 응답 shape | `adapters/*/` 인터페이스 함수의 반환 JSON | 공통부의 어댑터 응답 파싱·검증부 |
| 플랫폼 패리티 | `adapters/macos/` 출력 예시 JSON | `adapters/windows/` 출력 예시 JSON |
| send 상태 전이 | `docs/adapter-contract.md` 상태 머신 | 코드 전체의 `status` 설정 지점 |
| 에러 코드 | 계약의 에러 enum | 공통부 에러→메시지 매핑 + 어댑터 에러 반환 |
| 명령 출력 형식 | `docs/command-spec.md` + design 예시 | 공통부 렌더링 코드 |
| DB 매핑 | `docs/db-schema.sql` 컬럼(snake_case) | 어댑터 JSON(camelCase) → 저장 변환 |

## 우선순위별 체크리스트

### 1. 계약 정합성 (최우선)

- [ ] 각 어댑터 함수의 반환 shape이 `docs/adapter-contract.md`와 정확히 일치 (필드명·타입·필수 여부)
- [ ] 래핑 일치: 계약이 `{ rooms: [...] }`면 공통부가 `.rooms`를 꺼내는가. 계약이 `[...]`면 공통부가 배열로 받는가
- [ ] `roomId`가 양 어댑터 모두 `string`이고 공통부가 내부 구조를 해석하지 않는가 (인덱스 정수로 캐스팅, 파싱 시도 없음)
- [ ] camelCase(JSON) ↔ snake_case(DB) 변환이 한 곳에서 일관되게
- [ ] 공통부가 어댑터 응답을 **런타임 검증**하는가 (계약 위반 시 조용히 넘기지 않고 명확히 실패)
- [ ] 어댑터가 계약 enum 밖의 에러 문자열을 반환하지 않는가
- [ ] `outgoing`, `unreadCount` 등 불리언/숫자 필드의 의미가 양쪽에서 같은가

### 2. 플랫폼 패리티

- [ ] 같은 fixture 시나리오에 대해 macOS·Windows 어댑터 출력 JSON을 diff → 필드·순서·포맷 동일
- [ ] 타임스탬프 형식 동일 (계약이 ISO 8601 UTC면 양쪽 다 그것, 로케일 문자열 없음)
- [ ] 빈 결과 표현 동일 (`[]` vs 필드 생략)
- [ ] `null` 허용 필드(예: `memberCount`, `lastMessage`, `appVersion`)를 한쪽만 채우지 않는가
- [ ] 같은 실패 상황에서 같은 에러 코드
- [ ] 방 목록 정렬 순서 동일
- [ ] 사진/파일/이모티콘 메시지 처리 방식 동일 (둘 다 스킵이거나 둘 다 `kind: "unsupported"`)

### 3. send 안전 불변식

- [ ] 동명 방이 여러 개일 때 후보 목록에 **기본 선택값이 없다**
- [ ] 비대화형(`--yes`/파이프)에서 동명 방 다수면 전송하지 않고 종료 코드 5
- [ ] `--dry-run`이면 `sendText`(및 어댑터 전송 경로)가 **호출되지 않는다**. `pending` 로그도 안 생긴다
- [ ] `status: "unknown"`(SEND_VERIFY_TIMEOUT)에 대해 **자동 재시도가 없다**
- [ ] `--yes` 없이 편집기 모드는 미리보기 + `[y/N]` 확인을 거친다
- [ ] `--stdin` 빈 입력(공백만)은 전송하지 않는다
- [ ] `--max-chars` 초과는 전송하지 않고 알린다
- [ ] `status`가 상태 머신 경로로만 설정된다 (코드에서 `send_log.status`를 직접 쓰는 곳이 없다) — `grep`으로 전수
- [ ] 계약 상태 머신에 정의된 전이 중 코드에 없는 것(죽은 전이) 없음, 코드의 전이 중 계약에 없는 것(무단 전이) 없음

### 4. 명령어 스펙 준수

- [ ] 각 명령의 출력이 `docs/command-spec.md` / design 예시와 일치 (`✓ 개발팀에 전송됨  14:32` 형식 등)
- [ ] 종료 코드가 스펙대로 (0/2/3/4/5/6/7/8/9)
- [ ] TTY가 아닐 때 색/기호 처리가 스크립트 파싱을 깨지 않는가
- [ ] 오류 메시지가 세 부분(무엇이/왜/복구 명령)을 담는가

### 5. 개인정보

- [ ] 로그·stderr·에러 리포트·(있다면)텔레메트리에 **메시지 본문이 없다** — `grep`으로 로그 호출부 전수
- [ ] 별칭이 로컬 SQLite 밖으로 나가지 않는다
- [ ] `cache clear`가 지우기로 한 테이블만 지운다

### 6. 코드 품질

- [ ] 계약에 있으나 아무도 호출하지 않는 어댑터 함수/필드 (의도된 것인지 확인)
- [ ] 도달 불가능한 상태 분기 (`if status == "X"`의 X가 실제로 나올 수 있는가)

## 스크립트 대조 (general-purpose 타입 활용)

Grep + 스크립트 실행이 가능하다:
- 모든 어댑터 함수 반환 shape 추출 → 공통부 파싱 타입과 표로 대조
- `status\s*[:=]` 전수 grep → 계약 상태 머신과 대조
- 로그/print 호출부에서 메시지 본문 변수가 인자로 들어가는지 grep
- 두 어댑터를 같은 fixture로 실행 → 출력 JSON `diff`

## 실행 시점: 점진적

전체 완성 후 1회가 아니다:
- 공통부 모듈 완성 → 즉시 계약 정합성
- 어댑터 함수 완성 → 즉시 공통부 파싱부와 교차
- 양 어댑터의 같은 함수 완성 → 즉시 패리티
- 이유: 초기 경계면 불일치가 후속 모듈로 전파되기 전에 잡는다. 버그가 누적되면 수정 비용이 급증.

## 리포트 형식

`_workspace/qa/qa-report-{모듈}.md`:

```
## {모듈} — {날짜}

### 통과
- [항목]

### 실패
- [파일:라인] 기대: X / 실제: Y
  재현: [조건]
  수정 방향: [구체적으로]
  통지: core-engineer, macos-adapter-engineer (경계면이므로 양쪽)

### 미검증
- [항목] — 사유: 실제 카카오톡/OS 환경 필요
```

발견은 리포트에만 쓰지 말고 **해당 에이전트에게 즉시 SendMessage**. 경계면 이슈는 양쪽 모두에게. 계약 모호성이면 cli-architect에게 계약 수정 요청.

## 환경 제약

실제 카카오톡 앱/OS가 없어 동적 검증이 불가능하면, 정적 교차 비교로 가능한 만큼 하고 나머지는 **"미검증 — 환경 필요"** 로 명시한다. 검증 못 한 것을 "통과"로 적지 않는다.

## 이전 리포트가 있을 때

`_workspace/qa/`에 리포트가 있으면, 이전 실패 항목의 수정 여부를 먼저 확인(회귀 검증)한 뒤 새 모듈로 넘어간다. 계약 버전이 올라갔으면 새 버전 기준으로 재검증.
